# Codex challenge to Fable round 1

Your core verdict survives: keep the release engine and replace the content system. Before implementation, respond to these objections and refine the design.

1. **Reject the brand line “Verification is a military habit.”** It risks flattening a diverse military-family audience into a stereotype and can feel like military language pasted onto AI. Use the plainer narrative **“Show the work”** or a stronger human alternative. Military and family identity should come through place, schedule, people, service transitions, and practical constraints—not a rhetorical analogy.
2. **Do not publish a categorical tax-deductibility or 501(c)(3) assertion from ProPublica alone.** The record is compelling evidence, but the package does not contain the determination letter and the owner has not confirmed the EIN in this task. The redesigned site may show a carefully qualified organization-record row such as “Public IRS-derived records list Patriot Web Solutions, Killeen, under EIN 99-1238039; owner confirmation pending before production,” but the production claim and donation-receipt language remain gated. Prefer an official IRS TEOS link if a stable link can be verified. Never imply this review is legal advice.
3. **Avoid brittle vanity facts.** A live commit count such as “~850 commits” will go stale and communicates volume, not quality. The project record should show the repository, license, current status, the areas worth inspecting, an exact last-verified date, and specific verification artifacts. Use a pinned revision only where it matters.
4. **Do not replace card monotony with table monotony.** Ledger, syllabus, fact block, annotated artifact, prose, process diagram, development log, and comparison need distinct visual forms. The homepage should not feel like a compliance report.
5. **Public release hashes belong in a technical field note, not the homepage donor proof.** The homepage proof strip should emphasize the real repository, the three-hour weekly program design, the Killeen identity, and the publicly listed organization record. Put technical packaging receipts under the rebuild field note.
6. **Build substantial pages without pretending owner facts exist.** Use explicit internal data slots or production-checklist obligations for people, photos, dates, class start time, costs, impact totals, and private product listings. Do not let those missing facts become visitor-facing TODO prose. A page must still feel complete today.
7. **The Work section needs useful content now.** Hive Mind OS must have a full inspectable project record with real links. AI Developer Workbench and Coupon Hive need richer, dated record pages that explain purpose, current evidence state, lessons, what exists locally, and what publication requires—without inventing public availability. Add a visible “public listing not verified” state rather than vague “coming soon.”
8. **The learning program needs concrete artifacts.** Implement at least a six-week foundations syllabus, a repeat-until-understood readiness standard, sample portfolio contents, a skills-to-job-task mapping, and the defensive purpose of replay/leakage/reward-hacking/backtesting lessons. Clearly label a sample session as a proposed/default structure if no actual log exists.
9. **Audience journeys must result in visible page differences.** Learner, donor, employer/partner, custom-client, technical reviewer, platform reviewer, and mentor lenses should each find a named route and concrete proof. Avoid seven audience cards.
10. **Fix public professionalism.** Replace “My WordPress Website” in the local release, add social metadata and a stable organization record, remove all visitor-facing drafting instructions from privacy/terms, and ensure the pages do not claim Google/OpenAI approval or partnership.
11. **Preserve the strong engineering.** Nested project records require a reversible installer update. Keep activation inert, page-conflict revisions, durable checkpoints, modified-page preservation, legacy route control, sitemap isolation, and the exact-archive verification gates.
12. **Implementation must be visually reviewed at desktop and mobile.** A text-only code pass is insufficient. The next build round must update screenshots and be followed by a separate visual critique round.

Write `docs/claude-collaboration/ROUND-2-RESPONSE.md`. State what you accept, reject, or adapt. Produce the final implementation contract: exact pages/files/components, content requirements, evidence boundaries, test changes, and an ordered build plan. Do not edit site files yet.
