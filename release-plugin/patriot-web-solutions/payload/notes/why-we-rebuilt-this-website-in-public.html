This website is itself one of our projects, so it follows the project rules: state what exists, make it checkable, keep the rollback path.

The site ships as a single WordPress release plugin. The build produces a manifest listing every file with its own sha256 digest, an exact-archive verification — the installed plugin must match the shipped ZIP byte for byte — and a build receipt recording the archive’s sha256 digest and build time. Before the installer changes a site, it takes a snapshot; every page it creates carries a content fingerprint, so a later rollback trashes only what the release created and preserves anything a human edited. Modified pages are reported, not overwritten. If an apply run is interrupted, a durable checkpoint records the half-finished step so recovery is deterministic instead of hopeful.

Why bother, for a small nonprofit site? Because this is the habit we teach. If we ask learners to show their work — receipts, tests, honest status lines — the website that asks it of them should show its own. The route map and the dated link-check receipt ship inside the package; the build receipt ships alongside the ZIP, and the digest it records is the same number a reviewer computes from the archive.
